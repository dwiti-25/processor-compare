# Decisions

One entry per decision: date, decision, reason, who decided.

- 2026-11-06: Cores = Hazard3, Ibex, VeeR EL2 (professor).
- 2026-11-06: Software ISA = rv32imc_zicsr for all cores, because Ibex and VeeR EL2 can't disable C.
- 2026-11-06: Report two ASIC scopes: core-only macro and padded chip top.
- 2026-11-09: This round is SKY130 only; FPGA and SCL 180 deferred (Dwiti).
- 2026-11-09: ASIC flow runs on Dwiti's MacBook (arm64) through the LibreLane 3.0.17 Docker image; LibreLane's own Yosys step does the synthesis, so the synthesis numbers come from the same flow that will harden the cores (Claude Code).
- 2026-11-09: Pre-route timing estimate = LibreLane Classic flow, with default settings, run through floorplan (FP_CORE_UTIL 50%), global placement and `OpenROAD.RepairDesignPostGPL`. Then LibreLane's mid-PnR STA runs once more (inserted with `meta.substituting_steps`): placement-estimated parasitics, ideal clocks, LibreLane default `base.sdc` (0.25 ns uncertainty, 5% derate, IO delay 20% of period). `flows/sta_r2r_hook.tcl` (via `STA_EXTRA_CORNER_TCL_FILE`) reports the worst register-to-register setup path. Estimated fmax = 1 / (T − that slack), at the nom_tt_025C_1v80 corner only, because LibreLane's mid-PnR STA loads only the default corner. We use reg-to-reg because core-only IO delays are arbitrary; all-path WS is also recorded. Why not a pure netlist STA: LibreLane synthesis doesn't buffer, and OpenROAD `repair_design` without placement leaves VeeR's 8,264-fanout core reset and hundreds of other high-fanout nets unrepaired, giving nonsense paths of 60+ ns. Ibex reset fanout is 1,677 (Claude Code).
- 2026-11-09: Core-only synthesis tops are each core's vendor top with no memories. A shared thin wrapper with identical ports comes with the testbench (P1) and will be used for hardening (Claude Code).
- 2026-11-09: VeeR EL2 is configured with `veer.config -target=typical_pd -fpga_optimize=0` plus the overrides below. `fpga_optimize` defaults to 1, which removes all of VeeR's clock gating; that is wrong for ASIC, so it is off (Claude Code).
- 2026-11-09: VeeR EL2 is reported in two configs. `min` (primary, BTB off) matches Hazard3 and Ibex, which have no branch predictor. `bp` (typical_pd predictor: BTB 32 / BHT 128 / RAS 2) is a sensitivity point closer to how VeeR is normally built. Headline = `min` (Dwiti, 2026-11-09).
- 2026-11-09: Hazard3 multiplier = `MUL_FAST=1` (single-cycle multiply, MULH via the sequential divider). It's the closest match to Ibex `RV32MFast` and VeeR's pipelined multiplier. Default `MUL_FAST=0` would give a much slower, 32+-cycle multiply (Claude Code).
- 2026-11-09: Frontends: Hazard3 = Yosys `read_verilog` (plain Verilog 2005; yosys-slang turns its static functions, called from two always blocks, into multiply-driven flops). Ibex and VeeR EL2 = yosys-slang (`USE_SLANG` in LibreLane). sv2v is not needed (Claude Code).

- 2026-11-10: VeeR EL2 reported in two configs (Dwiti): "min" (no TCM/cache, the fair-comparison rule; used for ASIC) and "tcm" (ICCM at 0x0 + DCCM at 0x2_0000, 128 KiB each, VeeR's intended memory system; RTL sim only, behavioural banks in `cores/veer_el2/wrapper/veer_tcm_mem.sv`, preloaded like VeeR's own testbench).
- 2026-11-10: Common link layout split into code (0x0-0x1FFFF) and data/stack (0x20000-0x3FFFF), so one binary per benchmark runs on all cores, including VeeR "tcm" (its LSU cannot read ICCM). The other cores see one flat RAM; their cycle counts moved by under 2% after the re-link (all numbers re-run).
- 2026-11-10: crt0 marks region 0x8 (testbench MMIO) as side-effect in VeeR's `mrac` CSR, guarded by `mvendorid == 0x45` so the binary stays identical for every core. Without it VeeR's unified write buffer merges successive putchar stores (seen with TCMs). Benchmark cycle counts are unaffected (CoreMark cycles identical before and after).

- 2026-11-10: Layout runs (flows/synth.sh HARDEN=1) exclude `sky130_fd_sc_hd__clkdlybuf4s*` from PnR via `EXTRA_EXCLUDED_CELLS` (same for every core). Reason: OpenROAD repair otherwise uses these clock-delay cells as fanout buffers, causing the max-slew/cap and much of the ss setup failure (STATUS.md, Hazard3 baseline). This is a don't-use restriction, not a waiver (Claude Code, on Dwiti's request to fix with legitimate flow settings).
- 2026-11-10: fmax from a layout run = 1 / (T − worst register-to-register setup slack) in the post-route STA, reported at nom_tt_025C_1v80 (typical) and nom_ss_100C_1v60 (slow), plus max_ss (slow, max RC) in results/harden_results.csv. Sign-off "clean" requires all nine corners clean.

- 2026-11-10: Layout settings for all cores (flows/synth.sh HARDEN=1 PGRT=1 REPAIR_MARGIN=1): exclude clkdlybuf4s* from PnR, post-GRT design repair, max wire length 400 µm (post-GPL and post-GRT), 30% repair slew/cap margins, CTS sink clustering 10. Sign-off limits unchanged (max transition 0.75 ns, max cap 0.2 pF, max fanout 10). MULTICORNER (PNR_CORNERS) is a no-op for repair/CTS (they already use STA_CORNERS) and is not used.

## Patches
| Core | Patch | Reason |
|---|---|---|
| Ibex | `cores/ibex/patches/0001-ibex_top-unused-scramble-assign.patch` | `logic unused_scramble_inputs = ...;` in `ibex_top.sv` is a lint-only variable with a declaration initialiser that reads nets; yosys-slang rejects it ("reading net state during design initialization unsupported"). The patch makes it a continuous `assign`, with no functional change (the signal is unused). Applied to a copy in `build/patched/`; the submodule is untouched. |
| VeeR EL2 | `cores/veer_el2/patches/0001-lsu_ecc-tie-off-wdata-ecc-without-dccm.patch` | With `dccm_enable=0`, `el2_lsu_ecc.sv` never drives `dccm_wdata_ecc_hi_any` / `dccm_wdata_ecc_lo_any` (the encoders exist only in `Gen_dccm_enable`). LibreLane's Yosys synthesis check fails on the 7 undriven bits (it would be X in simulation). The patch ties both to `'0` in `Gen_dccm_disable`, like the other ECC outputs already tied there. With no DCCM these values feed only DCCM-write/ECC paths that are never used. |
