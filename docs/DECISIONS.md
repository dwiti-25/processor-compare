- 2026-11-09: Pre-route timing estimate = LibreLane Classic flow, with default settings, run through floorplan (FP_CORE_UTIL 50%), global placement and `OpenROAD.RepairDesignPostGPL`. Then LibreLane's mid-PnR STA runs once more (inserted with `meta.substituting_steps`): placement-estimated parasitics, ideal clocks, LibreLane default `base.sdc` (0.25 ns uncertainty, 5% derate, IO delay 20% of period). `flows/sta_r2r_hook.tcl` (via `STA_EXTRA_CORNER_TCL_FILE`) reports the worst register-to-register setup path. Estimated fmax = 1 / (T − that slack), at the nom_tt_025C_1v80 corner only, because LibreLane's mid-PnR STA loads only the default corner. We use reg-to-reg because core-only IO delays are arbitrary; all-path WS is also recorded. Why not a pure netlist STA: LibreLane synthesis doesn't buffer, and OpenROAD `repair_design` without placement leaves VeeR's 8,264-fanout core reset and hundreds of other high-fanout nets unrepaired, giving nonsense paths of 60+ ns. Ibex reset fanout is 1,677 (Claude Code).
- 2026-11-09: Core-only synthesis tops are each core's vendor top with no memories. A shared thin wrapper with identical ports comes with the testbench (P1) and will be used for hardening (Claude Code).
- 2026-11-09: VeeR EL2 is configured with `veer.config -target=typical_pd -fpga_optimize=0` plus the overrides below. `fpga_optimize` defaults to 1, which removes all of VeeR's clock gating; that is wrong for ASIC, so it is off (Claude Code).
- 2026-11-09: VeeR EL2 is reported in two configs. `min` (primary, BTB off) matches Hazard3 and Ibex, which have no branch predictor. `bp` (typical_pd predictor: BTB 32 / BHT 128 / RAS 2) is a sensitivity point closer to how VeeR is normally built. Headline = `min` (Dwiti, 2026-11-09).
- 2026-11-09: Hazard3 multiplier = `MUL_FAST=1` (single-cycle multiply, MULH via the sequential divider). It's the closest match to Ibex `RV32MFast` and VeeR's pipelined multiplier. Default `MUL_FAST=0` would give a much slower, 32+-cycle multiply (Claude Code).
- 2026-11-09: Frontends: Hazard3 = Yosys `read_verilog` (plain Verilog 2005; yosys-slang turns its static functions, called from two always blocks, into multiply-driven flops). Ibex and VeeR EL2 = yosys-slang (`USE_SLANG` in LibreLane). sv2v is not needed (Claude Code).

- 2026-11-10: VeeR EL2 reported in two configs (Dwiti): "min" (no TCM/cache, the fair-comparison rule; used for ASIC) and "tcm" (ICCM at 0x0 + DCCM at 0x2_0000, 128 KiB each, VeeR's intended memory system; RTL sim only, behavioural banks in `cores/veer_el2/wrapper/veer_tcm_mem.sv`, preloaded like VeeR's own testbench).
- 2026-11-10: Common link layout split into code (0x0-0x1FFFF) and data/stack (0x20000-0x3FFFF), so one binary per benchmark runs on all cores, including VeeR "tcm" (its LSU cannot read ICCM). The other cores see one flat RAM; their cycle counts moved by under 2% after the re-link (all numbers re-run).
- 2026-11-10: crt0 marks region 0x8 (testbench MMIO) as side-effect in VeeR's `mrac` CSR, guarded by `mvendorid == 0x45` so the binary stays identical for every core. Without it VeeR's unified write buffer merges successive putchar stores (seen with TCMs). Benchmark cycle counts are unaffected (CoreMark cycles identical before and after).

- 2026-11-10: Layout runs (flows/synth.sh HARDEN=1) exclude `sky130_fd_sc_hd__clkdlybuf4s*` from PnR via `EXTRA_EXCLUDED_CELLS` (same for every core). Reason: OpenROAD repair otherwise uses these clock-delay cells as fanout buffers, causing the max-slew/cap and much of the ss setup failure (STATUS.md, Hazard3 baseline). This is a don't-use restriction, not a waiver (Claude Code, on Dwiti's request to fix with legitimate flow settings).
- 2026-11-10: fmax from a layout run = 1 / (T − worst register-to-register setup slack) in the post-route STA, reported at nom_tt_025C_1v80 (typical) and nom_ss_100C_1v60 (slow), plus max_ss (slow, max RC) in results/harden_results.csv. Sign-off "clean" requires all nine corners clean.

- 2026-11-10: Layout settings for all cores (flows/synth.sh HARDEN=1 PGRT=1 REPAIR_MARGIN=1): exclude clkdlybuf4s* from PnR, post-GRT design repair, max wire length 400 µm (post-GPL and post-GRT), 30% repair slew/cap margins, CTS sink clustering 10. Sign-off limits unchanged (max transition 0.75 ns, max cap 0.2 pF, max fanout 10). MULTICORNER (PNR_CORNERS) is a no-op for repair/CTS (they already use STA_CORNERS) and is not used.

LibreLane's Yosys synthesis check fails on the 7 undriven bits (it would be X in simulation). The patch ties both to `'0` in `Gen_dccm_disable`, like the other ECC outputs already tied there. With no DCCM these values feed only DCCM-write/ECC paths that are never used. |

- 2026-11-10 (Dwiti): **Post-route repair step added to the layout flow** (flows/synth.sh `POSTROUTE=1`; same for every core). LibreLane Classic repairs only on pre-route parasitic estimates, and post-route RCX wire loads are much larger on some nets, so ss slew/setup failed with no way to fix them after routing. New flow `ClassicPostRouteRepair` (plugin `flows/llplugins/librelane_plugin_postroute`, loaded by LibreLane's plugin discovery) inserts after the first detailed route: `OpenROAD.RCX` → `PostRoute.Repair` → `OpenROAD.GlobalRouting` → `OpenROAD.RepairAntennas` → `OpenROAD.DetailedRouting`; the rest of Classic (fill, RCX, sign-off STA, DRC, LVS, all checkers) is unchanged. `PostRoute.Repair` annotates the RCX SPEF on all nine STA corners, runs `repair_design` (GRT_DESIGN_REPAIR_* margins: wire length 400 µm, 30% slew/cap) and `repair_timing -setup` then `-hold` (GRT_RESIZER_* margins, LibreLane defaults), re-legalises placement and removes signal routing so the design is fully re-routed. One repair pass. Sign-off limits unchanged. Bench check on the Hazard3 @40 MHz `_margin` design (repair step alone, on its RCX parasitics): slew/cap/fanout 2,795/3/2 → 558/0/0, worst setup WS −4.89 → −1.34 ns, hold unchanged (+0.09 ns); real numbers come from the re-routed sign-off. Tool versions unchanged (LibreLane 3.0.17 container). Whole layout setting from now on: HARDEN=1 PGRT=1 REPAIR_MARGIN=1 POSTROUTE=1 (Claude Code, on Dwiti's decision).

- 2026-11-11 (Dwiti asked for the fix; Claude Code): **Register-accurate activity mapping for post-layout power** (`flows/actmap.py`, used by `flows/power.sh` when a core has the inputs below). Literal SAIF-to-netlist name matching (`flows/saif2act.py`) left 149 of Ibex's 1,924 registers unmatched (default activity) and silently paired 26 more with the wrong RTL bit. Three causes and fixes:
  1. *Declared LSB ≠ 0* (e.g. `logic [31:8] rdata_q`): Verilator's SAIF renumbers bits from 0, the netlist keeps RTL indices. Fix: shift by the declared LSB, taken from a 1-cycle VCD header (`SAIF=1 TRACE=vcd DUMPLIMIT=1 flows/sim.sh <core> coremark_pwr`; VCD keeps declared ranges). Checked on `instr_addr_q[31:1]` (SAIF index 0 = RTL bit 1, the most active).
  2. *Unpacked arrays* (`mhpmcounter[32]×64`, `imd_val_q_i[2]×34`): SAIF `base[e][i]`, netlist one linear index. Fix: linear = (N−1−e)·W + i. Checked: minstret (element 2) = linear 1856..1919 (the only 64 counter bits present), and the unused `imd_val_q_i[1][33:32]` are exactly the linear bits 32..33 missing from the netlist.
  3. *FSMs re-encoded by Yosys* (`fsm_recode`, binary → one-hot: Ibex `mult_state_q`, `md_state_q`, `ctrl_fsm_cs`, `data_type_q`): netlist bit k ≠ RTL bit k. Fix: per-state cycles and transitions over the same CoreMark window from a testbench monitor generated from the Yosys log (`flows/actmap.py --gen-mon <yosys log> <svh>`; `SAIF=1 PWRMON=<svh> flows/sim.sh <core> coremark_pwr`), mapped through the encoding printed in the log (codes MSB-first; position k = netlist bit k, checked: the reset state's bit is the only set-type flop in each FSM).
  Result for Ibex @30 MHz post-route layout: 1,924/1,924 register outputs annotated (was 1,775), 0 unmatched; mapping printed in `results/raw/sky130/ibex/harden_default_wrap_30MHz_postroute/power_coremark/mapping.txt`. CoreMark power (nom_tt) 20.4 → 22.1 mW; the rise is almost all from the multiplier FSM's corrected duty (idle/ALBL state 95.8% of cycles instead of the ~2% implied by the binary bits), which makes OpenSTA propagate the ALU operands' toggling into the multiplier array; the counter/divider/rdata_q corrections each move the total by < 0.05 mW. The regenerated Ibex SAIF has the same window (448,506 cycles). Still zero-delay propagation (no glitch power). Hazard3 also has two recoded one-hot FSMs (`bus_gnt_ds_prev`, `power_ctrl.state`); its 10.2 mW still uses literal matching and should be rerun with this step (done 2026-11-18, below). VeeR not touched.

- 2026-11-18 (Dwiti asked for the FPGA handoff kit; Claude Code): **FPGA flow (P3) started**, in `fpga/` (Dwiti's choice of folder; CLAUDE.md's layout had `cores/<core>/fpga/`). Same core wrappers, configurations, patches and benchmark binaries as the ASIC flow. The source list comes from `cores/<core>/sky130/{sources.f,synth.conf}` through `fpga/vivado/sources.tcl`, which feeds both Vivado and the Verilator check. The PL shell (`fpga/rtl/fpga_shell.sv`) reproduces the testbench memory: 256 KiB RAM at 0x0, 1-cycle latency, the same MMIO, and the cycle and marked-window counters of `tb_top.sv`. So FPGA cycle counts should equal RTL simulation. Checked in simulation: `fpga/sim/run_sim.sh <core>` gives 52/52 programs identical to RTL sim for all three cores (exit code, console output, total and marked cycles; `results/raw/fpga/sim/<core>/summary.txt`). Part xc7z020clg400-1, which is PYNQ-Z1 and Z2 alike. The board and Vivado version are still open in PROJECT_FACTS.md. No PL pins are used, so the bitstream is the same for both boards.
  Two FPGA-only technology mappings of clock gating, the same function and cycle counts. They touch the "same config" rule; **approved by Dwiti on 2026-11-18** (both 1 and 2 below):
  1. *Ibex*: `prim_clock_gating` comes from lowRISC's own `prim_xilinx` (BUFGCE) instead of `prim_generic` (latch + AND, which would put the core clock on LUT fabric). It is the one gate in the "small" config, the core sleep gate in `ibex_top`. Ibex parameters are unchanged.
  2. *VeeR EL2*: config `min_fpga` = `min` + VeeR's own `fpga_optimize=1` (`cores/veer_el2/gen_config.sh min_fpga`; `-set=` because `typical_pd` forces `fpga_optimize=0`). The generated headers differ from `min` only by `` `define RV_FPGA_OPTIMIZE 1 ``. This turns VeeR's dozens of latch clock gates (`rvclkhdr`) into flop enables; a Zynq-7020 has only 32 global clock buffers. Checked: RTL sim of `min_fpga` is identical to `min` on all 52 programs, including total and marked cycles (`results/raw/sim/veer_el2_min_fpga/`). The ASIC flow stays on `min`. FPGA power for VeeR therefore has no clock-gating savings; Hazard3 has no clock gates, and Ibex's single gate is kept as a BUFGCE.

- 2026-11-18 (Dwiti asked for the rerun; Claude Code): **Hazard3 power rerun with the register-accurate mapping** (`flows/actmap.py`, same steps as Ibex: VCD header, FSM monitor from the Yosys log, `flows/power.sh hazard3 harden_default_wrap_30MHz_postroute`). The first attempt matched only 848/1,940 registers. Cause: Hazard3 goes through Yosys' own Verilog frontend (`FRONTEND=verilog`), which keeps memories two-dimensional in the netlist (`regs.real_dualport_noreset.mem[e][i]`, `frontend.fifo_mem[e][i]`), but actmap always applied the slang-style linear index (rule 2 above). Fix in actmap: an array the netlist keeps as `base[e][i]` is mapped element by element (bit = declared LSB + SAIF index); others are still linearised. Checked: Ibex's activity file and mapping report are byte-identical with the fixed script; Hazard3 register file x0 has zero activity, a0 is the most active of the registers checked. Result: 1,940/1,940 register outputs annotated (was 1,939), 0 unmatched; the bits whose RTL source changed are only the two recoded FSMs, with the same activity as before (`bus_gnt_ds_prev[1]` 0.2792/cycle) or none (`power_ctrl.state` never leaves state 0; the newly mapped `state[3]` is idle). **CoreMark power (nom_tt, 30 MHz) unchanged at 10.2 mW**; `power.rpt` is identical to the literal-matching run. So for Hazard3, unlike Ibex, literal matching was already correct; the rerun confirms it. The regenerated SAIF has the same window (363,251 marked cycles) and identical core activity; it only adds testbench-level variables. Mapping in `results/raw/sky130/hazard3/harden_default_wrap_30MHz_postroute/power_coremark/mapping.txt`. Also: `scripts/collect.py`, `scripts/md2pdf.py` and `flows/actmap.py` were never committed executable, though the Makefile and READMEs call them directly; now mode 755.

- 2026-11-18 (Dwiti approved the fix; Claude Code): **VeeR AXI adapter: no added latency** (`common/wrapper/axi2obi64.sv`, commit bcb0f10). The adapter registered every OBI response before presenting it on R/B, so each VeeR IFU/LSU read took 2 cycles (AR→R) from a 1-cycle memory, while Hazard3 (`ahbl2obi`) and Ibex (`obi32to64`) see the memory's 1 cycle. A response for the queue head is now presented in the cycle it arrives; one the master doesn't take is held in the queue and stays valid and stable (AXI rule). Checked: VeeR min 52/52 in RTL sim, CoreMark CRCs correct, same retired instruction counts (Dhrystone 196,023); min_fpga identical to min; FPGA sim 52/52 identical. CoreMark 14,642,602 → 12,369,671 marked cycles. The old figure is kept in LIMITATIONS.md as a diagnostic note.
  **Timing to watch:** this creates a combinational path from the memory's read data/valid/error into VeeR, through the adapter's `rdata`/`rvalid`/`rresp` muxes into the IFU and LSU (in the core-only macro, a port → core input path; on the FPGA, BRAM output → VeeR, inside one clock domain). In the core-only layout, check the input-to-register paths from `i_rdata`/`d_rdata`/`*_rvalid` in the STA reports, together with the SDC input delay; in Vivado, check `timing_paths.rpt` for BRAM→VeeR paths. If they limit fmax, don't loosen constraints: report it, and the choice is a registered response (2-cycle reads for VeeR, the old behaviour) for all cores or for none.
