# CLAUDE.md — RISC-V Processor Comparison (FPGA + SKY130 + SCL180)

Two-person student project at BITS Pilani (Dwiti Suchak, Ayush), supervised by
Prof. Govind Prasad. Read this file, then `docs/PROF_BRIEF.md`, `docs/PLAN.md`,
`docs/PROJECT_FACTS.md` and `docs/STATUS.md` before doing anything.

## What we are building

Three RISC-V cores, compared fairly on the same benchmarks, in three settings:

1. **FPGA**: PYNQ board (Zynq-7000), Vivado.
2. **ASIC, SKY130**: RTL-to-GDS with LibreLane (the successor to OpenLane 2),
   including an I/O pad ring.
3. **ASIC, SCL 180 nm**: same RTL, same flow steps, including I/O pads.

Compare area, timing and power everywhere it's feasible. Any core that can't go
through a stage gets a limitation note in `docs/LIMITATIONS.md`. Don't silently
skip it.

## Cores (confirmed by the professor)

| Core | Source | HDL | Notes |
|---|---|---|---|
| Hazard3 | github.com/Wren6991/Hazard3 | Verilog | Apache-2.0. Has Verilator tb and CoreMark port |
| Ibex | github.com/lowRISC/ibex | SystemVerilog | Needs sv2v or the Slang frontend |

Pin each one as a git submodule at a fixed commit. Don't edit vendor RTL. Put
any change in `cores/<core>/patches/` as a patch file, with the reason written in
`docs/DECISIONS.md`.

## Fair-comparison rules (never break these)

- **ISA**: compile all software for `rv32imc_zicsr`. All three cores support C,
  and Ibex and VeeR can't turn it off, so C stays on everywhere.
- **Configs**: switch off features the benchmark doesn't use where a core allows
  it (debug, PMP, B-extensions, caches, tightly-coupled memories). Record each
  core's final config and pipeline depth in `docs/DECISIONS.md`.
- **One binary per benchmark**: same source, same GCC version, same flags for
  every core.
- **Two hardening scopes, reported separately**:
  - *Core-only macro*: the core plus a thin wrapper, no memory. This gives the
    clean core-vs-core comparison.
  - *Padded chip top*: the core inside the same chip top for every core
    (clock/reset, small on-chip SRAM, UART, a few GPIO, power pads, I/O pad
    ring). This covers the professor's "including I/O pads" requirement. Keep
    signal pads to about 32 or fewer.
- **Clock targets**: the same sweep for every core, set per technology, with
  every point reported.
- **Tool versions**: the same versions for every core, recorded in
  `docs/VERSIONS.md`.

## Numbers integrity

- Every number in `results/results.csv`, tables, emails or the paper comes from
  `scripts/collect.py` parsing a tool report. Never type a result by hand,
  estimate one, or copy one from your own summary.
- Each row records: core, core commit, config, technology, scope (core or chip),
  clock target, run id, tool and PDK versions, and the report path.
- Never waive DRC/LVS errors, disable checks, or loosen sign-off settings to get
  a pass. If a run won't close, relax the clock or utilisation, log what you
  changed, and tell the user.
- If something looks wrong (for example CoreMark/MHz far from a core's published
  figure), stop and report it rather than tuning until it looks right.

## SCL 180 nm — special rules

- The SCL PDK is under NDA and is **not** in this repo. Its path comes from the
  environment variable `SCL_PDK_ROOT`, set by the user.
- **Don't open, print, cat, grep or summarise any file under `SCL_PDK_ROOT`**
  unless `docs/PROJECT_FACTS.md` says the lab allows it. Write scripts that
  reference PDK paths by variable, and let the user run them and paste back only
  the result summaries.
- Never commit PDK files, or reports that quote PDK internals, to git.
- The SCL flow may run on open tools (Yosys + OpenROAD, if the PDK has usable
  LEF/Liberty) or on Cadence Genus/Innovus on the BITS server. `PROJECT_FACTS.md`
  says which. Keep the flow steps matched to SKY130 so the comparison is fair.

```

scripts/collect.py           reports → results/results.csv
scripts/plots.py             results.csv → paper/figs/
```

Every flow must re-run with one command from a clean clone.

## Environment

- **ASIC (SKY130)**: Linux, or macOS via Nix. LibreLane with the `sky130A` PDK
  through ciel; OSS CAD Suite (Yosys, Icarus, Verilator, GTKWave); KLayout;
  sv2v; a RISC-V GCC toolchain; Perl (for VeeR).
- **FPGA**: Vivado runs only on x86 Linux/Windows, not macOS. Build in batch
  mode. The user runs the PYNQ notebook on the board.
- **Long runs**: start them inside `tmux` or with `nohup`, log to
  `results/raw/...`, and check the log rather than blocking on the run.

## Definitions of done

- **Synth**: Yosys synthesis on sky130_fd_sc_hd for each core, with cell count,
  area estimate and a pre-layout timing estimate in `reports/`.
- **Sim**: hello and the riscv-tests subset pass; CoreMark and Dhrystone give
  cycle counts; CoreMark/MHz is close to the published figure.
- **ASIC**: zero DRC, zero LVS errors, antenna clean, no setup/hold violations
  at the reported clock; area, cell count, fmax and power collected.
- **GLS**: the post-layout netlist runs hello and a reduced-iteration CoreMark,
  with output and cycle count matching RTL sim.
- **FPGA**: bitstream builds, timing is met, utilisation/fmax/power reports are
  collected, and the notebook is ready for the board.

## Working style

- Speed matters, so start long runs early and work on other things while they run.
- Before a phase, write a 3–5 line plan in `docs/STATUS.md`. After it, update
  STATUS.md with what passed, what failed, what is running, and what's next.
- Commit after each milestone.
- Ask the user before: deleting run directories, changing core selection or
  comparison rules, anything that needs accounts, licences, money or `sudo`,
  and anything touching the SCL PDK.
